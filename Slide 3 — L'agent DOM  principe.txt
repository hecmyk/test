Slide 3 — L'agent DOM : principe

Contenu (prose courte + petit schéma) :

Loop mono-phase (Python + OpenAI SDK, pas de LangGraph).

Le modèle reçoit le skeleton XML compressé dans le system prompt (pas tout le doc). Il émet des appels de tools pour aller chercher ce dont il a besoin, jusqu'à appeler submit_draft (finish-tool) avec sa réponse structurée.

Logique du prompt (décrite sans montrer le code) :

Cherche dans le skeleton une section qui correspond à la question → get_section
Si rien ne correspond → search par mots-clés
Réponds via submit_draft en citant la page source, ou en abstention explicite si l'info n'y est pas

Élément visuel : schéma boucle agent (system prompt + skeleton → LLM → tool_call → tool_result → LLM → ... → submit_draft)

Timing : 1.5 min

Slide 4 — Évolution des tools

Contenu :

Arc narratif du chantier, 3 versions :

v1 — get_section seul. Objectif : valider que le skeleton XML est navigable. Rien d'autre. C'était le point d'arrêt pour vous.

v2 — + search (BM25). Motivation : sur les docs longs, le skeleton ne suffit pas toujours à identifier la bonne section. On ajoute une recherche mot-clé qui renvoie top-k sections + snippets. Choix : collapse par section (pas par atom), pas d'atom_id retourné (évite une confusion syntaxique observée).

v3 — + get_visual (multimodal). Motivation : les charts et tables denses sont mal ou pas OCRisés en texte. On ajoute un tool qui renvoie crop image + texte OCR d'un élément visuel (table, chart, figure) sur appel d'un atom_id. L'agent décide seul quand appeler (routing libre, pas de règle rigide).

Élément visuel : timeline avec 3 étages, chaque tool ajouté figuré avec son signature courte

Timing : 2 min

Slide 5 — Le benchmark : FinRAGBench-V

Contenu :

Dataset EMNLP 2025 (arXiv 2505.17471), setup intra-doc oracle : chaque query est associée à un document et une ou plusieurs pages gold.

Filtrage appliqué : retrait des documents A3 (mise en page trop atypique, hors scope du pipeline). Reste : 467 queries sur documents financiers longs.

8 catégories de queries, réparties en 3 familles :

Text : Text-Inference, Text-MultiPage
Table : Table-Numerical Calculation, Table-Compare and Sort, Table-MultiPage
Chart : Chart-Information Extraction, Chart-Time Sensitive, Chart-Numerical Calculation

Deux types de réponses : short (287 queries) et long (180 queries).

Exemple concret rapide : "Selon le rapport, quelle est la croissance des revenus au T3 2024 dans le segment Asie ?" → gold_pages = [42], answer = "12.3%", category = Chart-Numerical Calculation.

Élément visuel : camembert par catégorie ou barchart n_queries par catégorie

Timing : 1 min

Slide 6 — Comment on mesure : judge + outcomes

Contenu :

LLM-as-judge : un LLM (GPT-OSS) compare la réponse de l'agent au gold pour chaque query, sort un score binaire (0 ou 1) + un reasoning.

Deux dimensions orthogonales :

judge_score : la réponse est-elle correcte au fond ?
page_ok : la page citée par l'agent (source_page) est-elle dans gold_pages ?

5 outcomes possibles par query (à mettre en tableau visuel sur la slide) :

Outcome	Condition	Sens
correct	judge_score = 1	bonne réponse
wrong	judge_score = 0, agent a répondu	mauvaise réponse
abstention	agent a mis tous les champs à null	reconnaît qu'il ne sait pas
error	crash technique (API, JSON malformé)	bug d'exécution
judge_failed	le judge n'a pas pu parser	à exclure du calcul

Métriques dérivées :

accuracy = correct / n_queries
page_recall_cited_only = page_ok / (queries où l'agent a répondu) → mesure la navigation quand l'agent s'engage
abstention_rate, forced_rate, etc.

Notes orales : "L'accuracy pénalise l'abstention comme un wrong — c'est volontaire, une abstention est une non-réponse."

Timing : 2 min

Slide 7 — Le dispositif de baselines

Contenu :

Idée centrale : les baselines ne sont pas 2 systèmes qu'on compare à l'agent. C'est un instrument de décomposition qui isole les sources d'erreur.

Contrat lecteur partagé (invariant méthodologique) : même modèle (mistral-medium-3.5), même température (0), même politique d'abstention, même schéma JSON strict. Seul le contexte donné au lecteur change entre les configurations.

4 configurations :

Config	Ce que reçoit le lecteur
oracle_md	Uniquement les gold_pages en markdown OCR
oracle_image	Uniquement les gold_pages rasterisées en image (150 DPI)
oracle_both	Les deux modalités fusionnées
fullctx	Tout le document en markdown OCR (map-reduce sur batches de 50 pages)

4 équations diagnostiques :

oracle_md − agent = ce que l'agent perd en navigation
oracle_image − oracle_md = ce que la vision débloque
agent − fullctx = valeur ajoutée de l'agentique vs brute-force
1 − oracle_both = plancher irréductible (raisonnement, gold ambigu, bruit judge)

Élément visuel : schéma en croix ou en table pour montrer les 4 baselines côte à côte

Timing : 2 min

Slide 11 — Caveats méthodologiques

Contenu :

Rigueur DS : dire ce qu'on n'a pas résolu.

Biais judge/famille. Le judge est GPT-OSS. Le run croisé (agent Mistral / judge Mistral) n'a pas encore tourné → le chiffre GPT-OSS agent (0.448) est potentiellement gonflé de 2-5pp par auto-favoritisme intra-famille. À trancher.
Ré-OCR des baselines. Les baselines re-OCRisent chaque page à part, substrat OCR différent de l'agent (qui utilise le stacking par page). Le gap oracle_md − run4 intègre cette différence, non isolable.
Fullctx : 1 batch perdu sur 429 (rate limit Mistral). Pas de retry ajouté volontairement — l'agent n'en a pas non plus, comparaison équitable en bruit d'infra.
Plafond irréductible = 44.7%. Même avec la bonne page + OCR + image + modèle multimodal, ~208 queries restent fausses. Décomposition qualitative (raisonnement / gold ambigu / judge indulgent-sévère) reste à faire.
Régression get_visual sur non-Chart. −4 à −14pp sur Text/Table quand appelé. Perte contenue (agent l'appelle rarement) mais optimisable.

Notes orales : "Le run croisé judge tourne encore, c'est ce qui permettra de figer le chiffre GPT-OSS. Le reste est du bruit méthodologique acceptable ou du travail suivant."

Timing : 1 min
